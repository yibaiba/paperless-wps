# 给外部 Agent 做清单的 MCP

日期：2026-09-27。状态：计划，尚未接入 MCP。

用户已明确用途：其他 Agent 根据客户需求，调用本平台制作和修改产品清单。本轮交付一个 MCP 服务，复用现有业务计算；产品事实、搭配知识继续在原后台维护。

## 1. Agent 与平台各自负责什么

Agent 负责理解客户要求、整理已知需求、提出候选选择、向客户澄清缺少的信息，并调用工具生成清单。

平台负责具体配置和出处、已维护的搭配检查、配套数量、已有设备抵扣、软件授权独立计量、部署/采购投影以及版本保存。计算仍由 Python 与 ZEN 完成。

核心路径：**查系统与产品 → 建清单草稿 → 选择和调整设备 → 检查配套与采购差异 → 应用选定配套 → 重查 → 保存 → 导出。**

## 2. 首版工具

| 工具 | Agent 用它做什么 | 后端基础与增量 |
| --- | --- | --- |
| `systems_list` | 查系统版本、角色和可用知识包 | 复用定义和知识包；历史系统名称标记未映射 |
| `catalog_search` | 按型号、参数、系统需求找产品；带草稿/角色上下文时查候选 | 复用产品查询和候选检查，补结构化过滤与分页 |
| `catalog_get` | 查看具体配置、关联搭配和原文依据 | 复用配置、来源及知识修订，按需读取详情 |
| `list_search` | 找到已有客户/项目清单，继续改单 | 复用项目列表，补摘要查询；同名不自动选中 |
| `list_create` | 新建清单草稿，或从已有项目指定修订复制草稿 | 新增最小服务端草稿记录 |
| `list_get` | 读取草稿或保存版本，查看设备、采购、缺项和依据 | 复用项目投影，补视图选择和检查记录读取 |
| `list_update` | 加产品、换型号、改数量、关联共用设备、拆分已有与采购、应用配套 | 将现有前端编排整理成后端业务命令 |
| `list_check` | 查兼容、缺件、容量、共享、数量及本次采购变化 | 复用现有检查和差异服务，返回固定检查记录/指纹 |
| `list_save` | 按已检查的草稿保存新项目修订，返回网页链接 | 复用项目保存，补写入幂等；不自动人工确认 |
| `list_export` | 从明确保存修订导出清单 | 复用部署/采购投影；Excel 文件导出需新增 |

系统定义或知识包尚未确认时仍可建立业务草稿：返回已知的历史系统/角色文本、来源及未映射状态，保持原有适配路径，不为接入 MCP 自动确认系统或搭配。

无项目上下文的产品搜索只返回产品事实；有明确角色、环境和版本上下文时才附适配结论。搜索排名、产品名称或能力标签不代表已验证兼容。

## 3. 最重要的三个工具

### `list_update`：表达业务操作

采用明确类型的操作，Agent 不需要传整份项目快照或图纸 XML：

- 设置房间、系统、角色及已知环境/规模。
- 选择具体配置及来源，明确设备类型、数量与供货来源。
- 用同一设备 ID 关联多个角色，或创建另一台独立设备。
- 修改数量、替换产品、复制为新设备、删除设备及对应引用。
- 按数量分配客户已有、本次采购和供货待确认。
- 选用/取消推荐或可选配套。
- 依据检查中的需求 ID，选择候选配套或关联已有设备。

需求、设备和来源使用稳定 ID。数量没有提供时保留为需求缺口，不擅自按一台创建设备。软件/授权/硬件/配件类型明确填写；已有硬件不能自动满足软件授权。

新增设备和删除设备复用图纸同步业务逻辑，已有项目的图形引用保持一致。普通图形布局不通过清单工具更改。

多个普通编辑可作为一次原子操作；校验失败整批不落库。配套应用必须对应有效检查指纹，前面的修改使数量失效时明确要求重新检查。

### `list_check`：把“为什么这样配”返回给 Agent

返回以下内容，不只返回一句“检查完成”：

- 所采用的草稿修订、产品/知识/系统定义版本及计算语义版本。
- 已选产品的适配结论、资源和共享检查、资料覆盖情况。
- 各项配套的范围、数量输入、需要量、已分配量、缺量和多余量。
- 配套候选及出处，哪些必须选、哪些可选，哪些依据仍未知。
- 全部部署、客户已有、本次采购及供货未定的数量。
- 相对保存基线的设备和采购差异。
- 可直接向客户澄清的缺失字段，例如系统版本、终端数、服务器环境、已有授权资格；问题必须关联具体角色/设备/规则。

本轮不新增 LLM 调用。澄清项由结构化缺口形成，外部 Agent 根据这些事实组织对话。

检查可以返回 `unknown` 或 `conflict`，这属于正常业务结果。数据库故障、引擎错误或输入引用无效则返回工具执行错误，不混成“资料不足”。

### `list_save`：可靠保存

保存携带草稿 ID、预期草稿修订、预期项目修订、检查指纹和幂等键。服务端按固定快照校验本次输入，与保存的检查记录保持一致。

有资料缺口仍可存草稿，保存结果和网页均显示待确认项。保存成功不能被 Agent 转述为“整套搭配已认证”。正式确认继续使用现有业务确认入口。

同一请求重试返回原结果，不能多存一个版本或多建一台设备。幂等回执与业务写入处于同一事务，先查原回执再校验旧修订。断线不代表回滚，调用方用同一幂等键恢复结果。

## 4. 最小状态与接口约定

服务端保存少量必要状态：

- 清单草稿：ID、配置、草稿修订、项目基线、固定资料版本。
- 检查记录：ID、对应草稿修订、结果、差异和指纹。
- 操作回执：幂等键、请求摘要、结果、产生的 ID/修订及调用来源描述。

优先复用现有实体与修订存储，必要索引增量添加。无需先完成完整协同编辑页面。Agent 保存后，用户能用现有网页查看项目；浏览器未保存的修改不会自动出现在 MCP 中。

每次写入带预期版本及可复用幂等键。两个 Agent 可以各做一份方案草稿；明确共同编辑同一草稿时，过期版本报错，禁止静默覆盖。凭自报客户端名称记录调用来源，不将其当成已认证操作者。

业务错误采用稳定代码及定位：版本冲突、检查过期、引用无效、幂等键内容冲突、执行失败。合法的资料缺口保留在检查项中。

结果默认摘要，参数、知识和出处按具体 ID 读取。数量使用十进制字符串和明确单位。分页说明未取完及续读游标；不把全库快照塞给模型，不静默裁掉结果。

`list_get` 可按 `devices / procurement / issues / evidence / changes` 读取对应视图。`list_check` 中的规则、来源和问题 ID 可通过同一读取入口展开，不要求外部客户端额外实现 Resources 才能完成业务。

MCP 调用方提交的是需求、选择和依据。检查状态、已确认知识、原始产品资料、规则结果及最终核算数量均由服务端提供。

## 5. 导出范围

先导出通用清单 Excel，不承担正式商务报价政策。每份产物固定项目及修订，返回文件 ID 和可访问的下载链接。

- 设备清单：房间/系统用途、产品、型号、配置、类型、部署数量、已有数量、本次采购、供货待定、单位与备注。
- 配套与待确认事项：需求依据、数量口径、缺件/多余量、兼容/容量/共享缺口。
- 版本与来源：配置修订、知识版本、原始工作表位置与项目保存修订。

同一共享设备只计一次；多个系统用途合并展示或另列关联表，不能按每个系统重复累计采购。已有设备保留部署行，采购为零。

价格列只有明确请求时列出原资料各价格字段，不自动选“最终成交价”。存在未知的清单允许导出，但显著标明草稿及缺口。生成文件必须能实际下载和打开，不能只返回不存在的文件名。

## 6. 实施顺序与验证

1. **读取与选型**：`systems_list`、产品查找/详情、清单查找/读取；抽取路由内已有查询编排，形成结构化工具结果。
2. **制作清单**：最小服务端草稿、编辑命令、检查及保存；复用原有图纸同步、快照和计算机制。
3. **交付清单**：新增 Excel 导出，真实 MCP 客户端跑完整流程，网页核对同一保存版本。

首轮只有一个 Python MCP 服务，采用官方 SDK。传输与调用方部署位置分别确定，业务工具保持一致。优先按本机 stdio 做协议验收；内网 Streamable HTTP 的部署与认证不扩大此次工具范围。

验收覆盖：

- 红盾 Windows + 会议预约，独立两台/共享一台/客户已有的部署与采购数量正确。
- 没有共享或数量依据时准确暴露未知，Agent 能读取具体缺口。
- 可选配套不选不采购；多个候选只计实际选择项。
- 软件授权独立；终端数增加补缺量，减少提示多余，不自动删除。
- 重复请求及进程重启不重复加量，过期草稿和检查不能覆盖新修改。
- 保存后网页清单、图纸、检查与 Agent 结果一致，旧确认修订不变。
- Excel 内容与指定保存修订一致，下载可用，未知和来源可见。
- 同一固定输入经 HTTP 和 MCP 的业务结果一致；错误明确，无假成功。

后端单项和单批测试继续 60 秒硬超时；协议契约、PostgreSQL 并发、真实客户端及文件打开分别验收。真实资料副本与合成测试知识分开，功能通过不代替真实搭配确认。

知识维护、模型设置、原始 Excel 导入、账号管理和通用画图工具不属于首版清单 MCP。Agent 如发现知识缺口，返回维护项及网页定位，交由现有后台维护。
