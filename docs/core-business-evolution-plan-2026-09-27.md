# 产品知识复用与售前核算实施计划

日期：2026-09-27。状态：计划，尚未实施。

依据：当前代码及 `core-architecture-review-2026-09-27.md` 的五项隔离复现。本计划覆盖核心业务演进，不将既有功能或待实施建议表述为已验收能力。

## 1. 本轮目标与范围

交付一条完整业务路径：

**从产品或系统维护知识 → 选择需求和候选 → 检查配套、容量与共用 → 区分已有设备和本次采购 → 修改并预览影响 → 保存可追溯项目版本。**

首轮贯穿案例采用红盾 Windows 无纸化和会议预约，包括独立服务器、共享服务器、客户已有服务器、软件和授权独立计量。其他无纸化版本继续可用，不能按同型号合并配置。共享兼容、容量和数量依据均采用资料或维护者确认结论，缺失时保持未知。

沿用 React、Ant Design、FastAPI 模块化单体、PostgreSQL、Python 业务判断、ZEN 数量计算与 draw.io。既有 AI 提取和搜索保留，但不成为核心业务步骤的前置依赖。

本轮不新增登录权限体系，不引入微服务、图数据库、Redis、LangChain、LangGraph、OR-Tools，不增加 AI 自动决策。正式报价、偏离表文档、完整音视频线材和定制制造核价为后续范围，本轮只明确其应复用的数据边界。

## 2. 固定业务约定

1. 未知不等于不需要，未填写数量不等于每台一个。
2. 检查通过、资料范围已核对、人工确认项目版本分别表示，不相互冒充。
3. 必需项纳入缺件检查；推荐和可选项在用户选用后才纳入本次需求，选用后的兼容和下游必需配套必须检查。
4. 共享以实际设备 ID 为依据；同型号不自动合并，已有设备也不自动满足软件授权。
5. 产品配置、知识依据、项目快照及计算语义均可追溯；旧项目更新先展示差异，再应用和保存。
6. 全部业务编辑进入同一草稿和撤销历史，清单与图纸不各存一套可独立修改的业务数据。
7. 真实业务知识与测试知识分库；功能流程通过不能代替真实搭配确认。

## 3. 五个交付阶段

### 阶段一：纠正检查和完成度语义

**数据与计算**

- 新增计算语义版本 3；新项目采用版本 3。冻结旧版本 1、2 的解释路径及回归案例，不把旧版本号指向新算法。
- 新录入配套的计算范围、方式、系数初始为空；保留“每台一个”“每系统一个”“按容量取整”的明确快捷操作。
- 配套拆分关系依据、候选依据、数量依据的确认状态。可以确认“需要服务器”，同时记录型号或数量未定；只有参与本次应用的条件、目标和数量有依据时，才生成可应用建议。
- 保留原 `status` 生命周期；对新版记录，confirmed 表示已审核所声明的事实，不自动使未确认的数量部分生效。完整程度由各部分计算，不靠整体状态推断。
- 在项目增加稳定的配套需求选择记录：需求引用、选用/不选用、备注。未选推荐或可选项展示为建议，不产生采购项；必需项不能通过“不选用”消除缺项。
- 增加启用条件，原有 `conditions` 保持为启用后的约束。首版显式替代分支只用于适用关系；配套使用启用条件和既有替代候选机制，避免建设通用流程语言。
- 启用条件为假：不适用；缺值：待确认。一个分支的约束同时满足；明确标识的替代组内任一分支通过即可。没有通过且仍有未知分支时为未知，适用分支全部失败时为冲突。独立约束继续同时满足，明确禁止关系不被允许分支抵消。
- 未进入任何适用分支不等于通过；仍按缺少适用依据处理。未知的禁止条件不能静默忽略。

**资料覆盖与项目确认**

- 为系统版本建立最小角色需求定义，区分基础角色和选中功能引出的角色；每个系统实例分别检查，避免项目里有一个角色就认为所有系统都完整。
- 按系统版本、角色及配置范围记录知识核对结果：未核对、有待确认项、已核对；明确“无需额外配套”需要单独事实及依据。仅检查本方案实际适用的维度，共享未使用时不要求共享资料齐全。
- 完成度分别返回 `known_checks`、`coverage`、`ready_for_confirmation`，不由计算函数直接设置人工 confirmed。
- 对已保存且满足确认条件的具体修订，提供显式确认操作，记录版本、计算指纹、维护人和依据。资料不足或冲突仍可保存草稿；人工确认是本次业务行为，不扩展成组织审批系统。
- 继续编辑产生草稿，旧确认版本不变。旧输出里的自动 confirmed 保留历史记录，但界面标为“历史计算状态”，不得当作人工确认记录。

**页面交付与验收**

- 快速录入直接显示数量是否已知、配套性质和适用范围；最后一步预览完整业务句子和数量口径。
- 项目分别展示必需缺项、未选建议、条件冲突、资料待确认及确认记录。
- 覆盖上一轮五项复现：省略公式不产生默认采购量；空规则不能证明无需配套；空系统角色提示缺口；未选可选项不阻碍完成；替代环境不互相冲突。

### 阶段二：产品与系统知识工作台

**稳定身份和复用结构**

- 将系统版本、角色和环境分支从显示文本提升为稳定 ID；阶段一的角色定义在此扩展为完整维护入口。保留历史文本和显式映射，重命名不改变关系。
- 建立轻量能力标识，用于产品能力与角色需求描述及候选筛选；能力标签本身不作为兼容通过依据。
- 以“系统版本 + 环境分支”组织知识包。知识包引用现有规则的 ID 和修订，定义角色、功能及覆盖结果；不复制为另一套规则，也不固定采购型号。
- 复用已有系列、类别、配置及排除选择器。共性规则仍只存一条，具体配置通过显式排除和补充关系表达差异；禁止使用最后修改覆盖冲突。
- 知识包发布固定成员修订；修改成员生成待发布变更，不静默改动已发布包或旧项目。
- 新配置落入系列时先显示适用范围及依据是否覆盖。不能仅因名称或系列相似继承已确认状态。明确覆盖整个系列的依据与仅核对现有型号的依据分别记录。
- 增加结构化证据引用：来源 ID/修订、工作表与行列或文档位置、原文片段、说明。继续保留历史自由文本，不自动捏造出处。

**维护操作**

- 提供产品视图与系统版本视图，编辑同一知识。
- 产品视图集中列出适用角色、必需/推荐/可选配套、数量口径、环境和共享条件，旁边查看来源。
- 系统视图集中列出角色、候选范围、功能选项、共性条件、配置例外及缺资料项。
- 支持多选配置共同维护、引用已有共性知识、复制为草稿、批量预览和发布。基于引用复用时不展开成每个型号一条副本。
- 批量操作展示新增、修改、排除、重复和冲突，整批使用预期版本和单事务写入；任一版本冲突回滚整批并定位记录。
- 沿用 `/knowledge` 入口，原平面表作为高级/历史视图保留。新增关系仍调用同一知识业务服务。

**验收**

- 一次维护一条有依据的共性关系能服务多个配置，配置例外不会污染其他型号。
- 同型号的不同系统版本仍独立；重命名系统或角色后引用不丢失。
- 新配置、复制知识及未核实来源不被自动确认为可用。
- 售前可从项目待确认项直接跳转到准确的产品、角色或知识，不必重新搜索。

### 阶段三：部署与采购分开核算

**模型变化**

- 继续复用现有 `Deployment`、`AccessoryAllocation` 和设备使用投影，不新建另一套设备台账。
- 对设备增加供货分配项：稳定 ID、设备 ID、数量、来源类型及依据。首版类型为本次采购、客户已有、供货待确认。
- 批量非共享设备可以拆分数量，例如需要 10 台、已有 4 台、本次采购 6 台；共享服务器继续按单台实例维护。
- 各供货分配之和核对部署数量；少量为供货未定，多量为冲突，均允许草稿保存。检查不自动补齐或删除分配。
- 增加设备时用户明确选择来源；沿用项目设备只增加使用关联，不新增采购数量。历史设备的供货来源先标记待核对，不能仅根据“曾经手动添加”猜为客户已有。
- 软件与授权分别维护供货来源及使用资格；已有硬件不代表已具备本次软件授权。

**两类投影**

- 设备清单：全部部署、数量、所服务系统及配套关系。
- 采购清单：仅包含明确由本次采购提供的数量；供货未定单独列出。
- 同型号可在展示中汇总，但汇总必须可展开设备和来源，不改变底层设备身份。
- 图纸引用部署设备，继续展示客户已有设备；移动、复制图形引用不改变采购，复制为新设备才增加部署并要求确定供货。

**验收**

- 两台独立服务器为两个设备；显式共享为一个设备服务两个系统。
- 客户已有共享服务器在部署与图纸中保留，本次采购为零；缺少共享依据仍显示未知。
- 软件、授权和配件独立计数；10 台需求、4 台已有、6 台采购的投影正确。
- 删除服务器同时处理其配套和供货关联，两个系统恢复缺项；撤销、重做及保存重开一致。

### 阶段四：计算解释与改单预览

**统一计算记录**

- 扩展现有检查结果，包含需求和范围 ID、输入值与单位、产品修订、知识修订、公式、计算语义版本、来源引用、已分配量和缺量。
- 复用一份结果供检查卡片、设备详情、清单和变更说明使用，不分别实现公式。
- 稳定的需求身份独立于展示名称及易变数量；规则修订后是否仍为同一需求通过显式关联表达，不能按型号或名称猜测。

**改单流程**

1. 选择已保存版本作为基线，修改产品、数量、环境、供货或配套选择。
2. 以固定的产品/知识版本完整重算，展示旧值、新值、变化原因、涉及角色和清单差额。
3. 对新增配套、数量增减和失效关联提供操作预览；减少数量不自动删除已采购项。
4. 确认应用到统一草稿，可整次撤销；保存时校验预期版本，生成新修订。
5. 原确认版本保持不变，新修订另行确认。更新知识或算法同样先预览影响。

**历史与最新目录**

- 历史方案复核只使用固定输入和对应计算语义。
- 查找替代产品明确标识使用当前目录；选入后将具体配置修订写入草稿。
- 旧项目不能表达的新规则不通过旧语义静默执行，先展示升级要求和差异。

**验收**

- 增加终端后能定位相关授权、容量和配件变化；所有差额均可追溯到输入或规则变化。
- 未应用预览不修改项目；过期预览不能覆盖较新的草稿或项目版本。
- 产品、知识或算法更新不改变旧确认版本；同版本输入重复检查得到相同业务结果。
- 本轮输出结构化改动清单及页面查看，不承诺完成公司正式改单、报价和偏离表模板。

### 阶段五：贯穿试点与架构收口

- 在隔离数据库运行真实资料副本：红盾 Windows 与会议预约独立部署、尝试共享、客户已有服务器、终端数量变化、可选配套选择和取消。
- 无共享、容量、授权等依据时准确返回待确认，不补测试规则到真实知识。
- 另一套隔离测试知识验证完整通过、资源超量、禁止共享、不同环境分支及已有数量抵扣。
- 真实客户验收使用房间、系统版本、终端数、部署环境、已有设备和共用要求；资料尚未提供时，明确将该项标为未验收，其他实施和隔离验证照常完成。
- 更新现有架构与业务流文档，纠正把设备清单描述为采购清单、把自动检查状态描述为人工确认的旧说法。

## 4. 随功能同步进行的内部整理

不先做大规模重构。每个阶段只整理其涉及的责任边界，保持现有 feature 归属。

| 责任 | 调整方向 |
| --- | --- |
| 路由 | 处理 DTO、版本错误及事务入口；数量引擎从组合入口注入，不从另一组路由导入 |
| 应用服务 | 编排读取、固定版本输入、检查、预览、应用和保存；数据库依赖注入 |
| 业务计算 | 纯函数接受不可变计算上下文，返回检查和建议；不改输入、不访问数据库 |
| 存储 | 产品、知识、项目和历史读取写入；保留原子事务和乐观并发 |
| 投影 | 从同一配置产生设备使用、设备清单、采购清单、图纸和改动说明 |
| 前端 | 共用业务操作和撤销历史；图纸布局变化不触发数量变化，检查结果按草稿指纹显示 |

具体处理：

- 将 `prune_stale_allocations` 从纯检查链移出；删除设备等操作明确清理相关引用，其他失效关联通过预览应用，均进入撤销历史。
- 项目检查只返回结果；记录快照等持久化行为由外层用例负责。历史读取不隐式迁移配置或重命名关系。
- 前端异步请求携带草稿指纹，响应只对应发起时的草稿；用户已改动时显式提示结果过期，不把旧响应覆盖新状态。应用配套和图纸更新作为一次可失败、可重试的业务操作提交。
- 固定一次计算中的知识、目录修订和设备索引；先测量候选、检查、保存耗时及查询数，再做按 ID 批量加载和摘要/详情分离。
- 沿用集中 Query Key，按产品、知识包或项目精确失效。暂不引入跨请求缓存和增量重算引擎。
- 稳定身份与高频查询可增加结构化表或索引，修订快照继续保留 JSON；不重建数据库，不追求将所有字段一次拆表。

## 5. 接口与迁移约定

沿用 `/api/configuration` 命名空间以及现有知识、候选、检查、应用和项目保存接口，增量扩展请求和响应；禁止静默丢弃新字段。

| 能力 | 最小接口变化 |
| --- | --- |
| 系统、角色及能力定义 | 增加版本化定义查询/维护，旧文本由显式映射适配 |
| 知识工作台 | 增加产品/系统筛选、证据引用、知识包读取与发布 |
| 批量维护 | 在已有批量接口上增加预览及新增能力，携带原修订、预览指纹和幂等操作标识 |
| 项目检查 | 返回各维度状态、覆盖缺口、供货缺口、计算解释及固定版本清单 |
| 项目应用 | 扩展可选需求选择、供货分配、关联清理；继续验证计算指纹 |
| 版本比较 | 增加基线修订与草稿/目标修订比较接口，返回业务差异和建议操作 |
| 项目确认 | 确认已保存修订，校验预期版本和检查指纹，不修改该修订内容 |

迁移步骤：

1. 开始实施时记录实际数据数量、版本分布与当前回归基线，不把旧对话统计当成现状。
2. 增量建表/字段，保留旧产品、来源、规则和项目 ID；脚本提供预览和可重复应用。
3. 旧系统/角色字符串按明确业务范围建立映射；同名不同版本不合并，歧义进入人工核对表。
4. 历史数值、公式和状态原样保留。无法证明数量依据的记录列入迁移核对，版本 3 不将“历史上填过 1”自动当作数量已审核；旧语义仍可重现旧结果。
5. 现有快照不改写；项目升级先展示身份映射、公式依据、可选项、供货来源和输出状态差异，应用后另存修订。
6. 旧接口能无损适配则继续工作；不能表达的新语义返回具体字段/版本错误。已有旧项目继续使用旧流程，不能因发布新代码被隐式转换。

## 6. 验证与完成标准

**自动化测试**

- 每项后端测试及每批命令均使用 60 秒硬超时；按领域拆批，不能通过取消超时获得成功。
- 增加数量未知、替代分支、未选可选项、需求覆盖、供货抵扣、确认修订、差异预览及版本升级测试。
- 对纯检查验证输入不变、相同版本结果一致；对预览验证无业务写入；对应用验证指纹、幂等和原子回滚。
- API 契约覆盖知识批量、候选、检查、配套应用、供货、比较、保存和确认，包含并发冲突及明确错误。
- 迁移用独立数据库验证两次执行不重复，旧快照不变，版本 1、2 原案例不被版本 3 改写。
- 前端执行 TypeScript 检查、生产构建及相关状态测试。真实浏览器覆盖知识工作台和完整项目流程，特别验证慢请求期间修改草稿、失败重试、撤销/重做及保存重开。

**业务验收**

1. 有依据的共性知识维护一次，可供多个配置和项目引用，例外有明确边界。
2. 缺数量、候选或共享依据时准确显示未知，不产生默认配套或假通过。
3. 独立两台、共享一台、客户已有一台的部署和采购计数正确，软件授权分开处理。
4. 可选项不选不采购，选中后完整检查其自身及下游必需配套。
5. 每条采购量可以解释其需求、来源、算法和已有抵扣。
6. 修改后先看到影响，应用、撤销、保存、重开与图纸一致。
7. 软件流程、隔离测试知识和真实业务确认分别列出结果；没有真实客户数据或搭配依据时不宣称业务已完全验收。
