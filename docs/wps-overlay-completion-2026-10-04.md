# WPS 浮层补全收尾记录 · 2026-10-04

## 路线与范围

用户选择先完成原有方式。本轮暂停原生编辑探针，继续使用生产加载项中的 WebDialog 浮层，不将其描述为原生单元格灰字。没有新增模型调用或训练，也没有用模拟宿主的成功结果代替真机验收。

## 已修复

- 按服务端 `primary_suggestion_id` 选择主建议，不再假设候选第一项必然是主建议；有其他备选不等于当前产品身份有歧义。
- 只为当前单元格可直接接受的产品显示灰字。跨行修改显示位置与理由；需要确认的修改显示「Tab 查看修改预览」，不伪装成一次 Tab 自动写入。
- 预览自动获得焦点，支持 `Ctrl/Cmd+Enter` 确认、`Esc` 或按钮返回输入；同一预览复用操作编号，保留既有事务日志与幂等应用。
- 模板表头、数量、备注、公式、合并单元格及未管理列不作为产品输入区。业务建议仍可定位数量等目标，但该位置的输入框只读，必须通过差异预览应用。
- 任务窗格新增重新打开当前单元格浮层的入口；补全窗口故障会显示错误。两条补全路径都有查询重试入口，不自动重放失败的写入。
- 焦点在取消预览、重试查询后回到输入框；不增加重复宿主事件订阅。

## 尚未验收

- 本轮没有控制 WPS 真机完成连续接受或实际工作簿写入。真实 WPS 焦点、滚动定位、20 次连续接受、100 次无候选 Tab、中文输入法和多窗口仍待验证。
- Windows 售前实际构建、本轮三类真实模板和业务确认轨迹未验收。自动化数量不代表真实业务推荐准确率。
- 原生编辑缓冲区、无焦点灰字和编辑态 Tab 能力仍未通过；本次路线不以这些能力为交付前提。
- 现有 WPS 窗口是否已载入最新资源、用户个人令牌的实际请求链路尚未核验。测试使用「售前产品助手」，不是「原生能力验证」加载项。

因此本轮结论是：浮层路径的代码、构建、组件和后端回归已验证；不能宣称 Cursor 原生补全或双平台试点全部通过。

## 继续完善：选择一致性与故障恢复

第二轮修复了两条可复现的控制流问题：方向键明确选择后按 Tab 原先绕过了候选重新校验；工作簿已经写入成功后，刷新下一步的异常原先与写入异常混为一谈。

- Tab、Enter 与候选点击共用选择校验与动作分派，沿用宿主操作编号去重。唯一、可直接接受的当前行结果可应用；跨行先定位；数量和业务联动仍须预览。
- 重新校验返回多个待选方案时继续展开，不取第一条替用户作决定；仍不可应用的结果显示真实问题，不把人工选择当作忽略兼容性检查。
- 选择请求保留取消信号、请求序号、文件/项目身份、工作簿业务修订和当前浮层会话校验，避免切换单元格后旧响应应用到已离开的上下文。
- 写入成功、刷新失败明确提示「本组修改已写入，但下一步刷新失败」，保留已应用日志；只由用户重试查询，不重复执行写入。实际写入失败仍显示原事务的回滚或恢复结果。
- 校验中及输入法组合中候选不可点击接受；错误区为消息与重试按钮保留两行状态高度，避免按钮藏到滚动区域。

## 继续完善：候选辨识与跨行选择保留

第三轮修复候选同名难以区分、明确选择后定位又回到通用候选列表，以及长列表方向键高亮移出视口的问题。

- 将业务候选展示提取为独立组件和纯展示函数。使用服务端产品变更中的配置/来源快照，显示配置说明、来源工作表、行号和导入批次；缺少说明或位置时明确显示缺失及对应 ID，不推测配置。悬停提示保留完整文字与配置、来源 ID。
- 业务候选每项三行；默认仍为灰字，只有展开时占用列表高度。方向键只滚动候选容器，保留输入焦点，旧基础补全与差异预览的高度不变。
- 显式选中的配置只在准确的目标工作簿、项目绑定、模板修订、单元格、浮层会话及本地业务修订内保留。定位后携带具体配置和来源重新请求预览，不复用无选择条件的预取，不复用旧预览直接写入。重新输入、撤销、应用或业务编辑会清除此临时选择。
- 仍按新预览的适用状态决定行为：跨行先定位，当前行的可接受结果才可 Tab 写入，需要确认的结果仍必须预览。

## 继续完善：撤销缓存一致性与预取取消

第四轮先在实际组件测试页复现：接受第 3 行产品 A、定位第 4 行、在浮层按 Cmd+Z，单元格和日志已经撤销，查询仍因缓存中的 A 报「第 3 行尚未确认具体产品配置」。该测试宿主不派发写入回调，用来验证组件不能只依赖宿主事件刷新自己的事务结果。

修复内容：

- 应用与撤销显式按工作表、行号去重刷新受影响行，不再按每一个单元格补丁重复读同一行。插件事务期间的同步回调不额外读行、不记录成手工数量编辑；真实外部编辑继续沿用事件更新。
- 一组刷新开始前将所有受影响行标记为待重读。宿主读行失败会抛出真实错误；重试查询时先重读这些行，不返回旧缓存。无需重新全表扫描。
- 撤销前取消当前查询和预取、恢复原生 Tab、清除旧建议。撤销成功但刷新失败单独提示，保留 undone 日志；查询重试不重复撤销。发生手工修改冲突时仍拒绝覆盖，并保留 applied 日志。
- 按 React 请求生命周期规范，将被当前查询接管的预取绑定到该查询的取消信号；新输入、撤销或组件退出时可取消请求。请求完成后移除取消监听器，不隐藏网络错误，也不将取消等同于成功。
