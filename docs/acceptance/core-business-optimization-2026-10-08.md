## 完整检查性能

使用既有 `benchmark.py`、相同机器和固定 100／500 行数据，每组 9 次，取中位数。优化保留完整用途验证和追溯，查询数没有增长。

| 行数 | 决策路径 | 墙钟旧→新 ms | CPU 旧→新 ms | 查询数 |
| --- | --- | ---: | ---: | ---: |
| 100 | Python | 192.69 → 106.57 | 150.76 → 102.71 | 14 |
| 100 | ZEN | 223.14 → 163.70 | 169.01 → 135.13 | 18 |
| 500 | Python | 860.90 → 581.91 | 704.80 → 493.43 | 14 |
| 500 | ZEN | 1004.63 → 601.79 | 744.36 → 569.23 | 18 |

主要修改是报价采用只复制实际修改的分支、检查问题使用固定字段生成稳定标识、用途投影复用一次规范序列化。精简检查响应保留未通过检查、设备消费者和数量摘要，完整追溯继续保存在草稿并按设备分页读取。

500 行精简响应由 5,109,946 字节降至 3,031,426 字节，减少 40.68%。完整响应仍为默认值，保持旧调用方兼容；网页需要显式请求摘要模式。

性能阶段回归分两批 35／23 项，共 58 项通过；单项与批次均使用 60 秒硬超时。桌面 Excel／WPS 不属于本阶段性能结论。

## 售前页面与草稿

网页完整检查改为先在工作草稿保存完整追溯，再向主页面返回精简结果；设备详情按草稿修订和设备 ID 读取完整用途。检查调用具备独立幂等回执，响应丢失后用原操作标识重试，不会把后来修订伪装成原结果。

项目页收口为“需求与系统、配置与配套、报价与导出”三个主阶段。系统定义及历史维护入口收进高级抽屉；draw.io 首次进入图纸时才挂载，切回清单后实例仍保留。真实浏览器验证中，进入项目时 iframe 数量为 0，首次进入图纸后为 1，切回清单后仍为 1；报价工作表按需加载并成功渲染公司表头和 10 列清单。

草稿同步状态统一为 `idle / creating / syncing / failed / conflict`，配置指纹按不可变对象缓存，避免同一修订在页面、同步和请求层重复序列化。前端 110 项测试、生产构建、后端网页草稿 12 项测试及 Ruff 检查通过。报价工作表构建预算由 `npm run check:bundle` 验证，同时禁止引入 Univer Pro 和非中文显式语言包。
