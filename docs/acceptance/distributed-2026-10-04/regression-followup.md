# 分布式与 37 项清单持续回归

日期：2026-10-04。基于提交 `7ff57db` 后的资料副本继续测试。所有项目、数量、分配及导出使用隔离 SQLite，未修改正式业务知识、价格、原始工作簿或旧客户项目。

## 发现并修复：分配后的容量被合并

触发方式：同一清单行包含两台 AHL-E36，各分一台给两个房间；两个系统分别需要同时充电 48 台和 12 台。

修复前，计算把两份需求合为 60，拿两台柜的合计容量 72 比较，返回通过。实际上第一间只有一台、容量 36，不足 48。剩余一台未分配库存时同样可能误判。

先补失败回归，复现两种情形失败，再修复：明确按数量独立分配且指标按单台容量计算时，逐角色使用已分配数量检查容量。现在第一间为冲突，第二间通过；结果保留真实角色 ID 和原文证据。

边界回归：

- 同型号的两条独立设备记录分别计量；不按型号合并。
- 一台设备明确共用时仍合计需求，缺共享依据仍显示资料不足。
- 同一角色分给不同规格的柜子但没有资源分配依据时，保留资料不足，不假定按比例分配。
- 设备总量减少造成分配超量时，单独返回分配冲突。
- 只有已分配设备参与对应容量；未分配库存不能弥补某房间不足。
- 原“整个部署”容量口径、历史 Python 调用默认行为保留；单位、汇总方式和容量范围不一致仍报冲突。
- 客户已有设备参与容量计算，采购数量为零；未知容量不会返回通过。

生产修改局限在既有用途检查结果到容量计算的传参，以及资源分组计算。沿用 ZEN 容量判断，没有新增规则、推测兼容或调整报价计算。既有较长的 `evaluate.py` 仅复用其已有独立分配判定并传参，没有拆分或重写整套检查管线。历史保存内容不被改写，重新执行检查时采用修复后的计算。

人工代码复核检查了分配标记、单台与整组容量、共享单实例、混合单位、真实角色 ID 恢复及副本隔离；本批未发现尚未修复的阻断问题。容量之外的共享、采购及历史存储规则未改动。
