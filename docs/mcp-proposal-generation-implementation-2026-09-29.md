# MCP 需求驱动方案生成：实现与验收记录

日期：2026-09-29。业务库只读核对；测试产品、价格、共享知识及项目均使用隔离数据库。

## 已实现的软件流程

外部 Agent → systems_list 读取需求描述 → list_update / requirements_patch → list_plan → list_get 查看方案、问题和依据 → list_update / proposal_apply → list_check → list_save → list_export。

- 保留原有十个 MCP 工具，新增 `list_plan`；HTTP 和 stdio 进入同一个 ListApplication 和项目业务服务。
- 不调用模型；Python 选型与回溯，现有 ZEN 计算数量，Decimal 计算金额。未增加依赖、后台进程或数据表。
- `list_proposal` 使用现有通用实体和修订存储。提案保留输入版本、原草稿、候选分支、逐行依据、问题、差异、价格快照与指纹；生成不修改实际设备。
- 原配置增加兼容默认值：需求来源、偏好、房间／项目数量输入；设备增加生成来源与人工型号／数量锁定。旧数据不重写。
- 系统角色可维护数量依据与配套满足关系；知识包可维护有条件的推荐顺序。来源引用校验来源存在及摘录原文。原包固定修订不会自动升级。
- 组合按确认的推荐顺序枚举，通过完整业务检查排除后续冲突，再读取下一可用分支。没有完整推荐依据时返回待确认推荐顺序，不将 ID 排序当成公司推荐。
- 配套递归展开；必需数量未知不生成一件；可选项未启用不采购；循环返回具体依赖路径。API 分页不截断内部候选计算。
- 配套满足角色可与同一实际服务器绑定，消除“软件配套服务器＋服务器角色”重复采购。共享由实际设备 ID 和原共享／资源检查判断。
- 明确允许复用的已有设备及确认的已含内容按量抵扣。已有配件不足时只为剩余量建立新设备；原供货不变。没有明确采购依据时，新设备保留供货未知。
- 提案采用为独立原子业务操作：校验草稿修订、基线、指纹及新价格修订，成功后进入原草稿撤销、保存和图纸投影；不允许整批操作中夹带另一份配置快照。
- 人工换型、数量及调整价保留；冲突明确展示。需求为零或设备不再使用时保留待移除项，只删除明确选择的生成设备；同步清理图纸及报价引用。
- 新价格采用与旧报价分开；待询价使用明确的缺价状态，不沿用旧价，也不伪装成 Excel 导入价。提案生成后价格被更正会要求重新生成。

## MCP 调用契约

MCP 参数仍包在 `request`，HTTP `POST /api/list-tools/{tool}` 直接使用 request 内容。原工具的参数方式不变。

1. `systems_list` 指定 `definition_id` 和 `knowledge_package_id` 后，需求描述中返回角色、功能、输入类型／单位、数量依据、配套满足关系及 `generation` 支持缺口。产品约束使用目录中的配置 ID，不能使用臆造型号。
2. `requirements_patch` 使用稳定房间／系统 ID；同 ID 更新，同名不同 ID 不合并。`systems[].roles` 只改变对应角色环境／资源。`features_confirmed` 表示是否已核对功能选择。
3. `generation.sources` 区分客户原文、资料原文和 Agent 待确认理解。待确认理解只记录，不改变对应有效字段，并形成客户问题。`generation.preferences` 按需求 ID 指定／排除配置、允许复用的设备与来源依据。提供 generation 时提交该域完整值，保留未修改的来源和偏好。房间数量引用房间 ID 与 `inputs.参数键`；项目数量引用 `project` 与 `project_inputs.参数键`；预算引用 `project` 与 `generation.budget`。
4. `list_plan` 示例（ID 和修订均取实际调用结果）：

```json
{
  "request": {
    "draft_id": "草稿ID",
    "expected_revision": 3,
    "operation_id": "调用方唯一操作ID",
    "deployment": "independent"
  }
}
```

返回 `proposal_id`、`fingerprint`、`input_versions`、`option` 和 `next_offset`。读取下一分支时携带同一提案 ID、部署方式及返回的 next_offset；提案持久化不增加实际草稿修订。`shared` 会比较共用与独立分支，仍以实际检查结果为准，不表示已认证共用。

5. `list_get` 新增视图：`proposals`、`proposal_lines`、`proposal_questions`、`proposal_decisions`、`proposal_changes`。指定提案时传 `proposal_id`，明细视图另传 `option_id`，沿用 offset／limit。问题含稳定 ID、code、recipient、objects、missing_fields、choices、evidence 和 action。
6. 整批采用：

```json
{
  "request": {
    "draft_id": "草稿ID",
    "expected_revision": 3,
    "operation_id": "采用操作ID",
    "operations": [{
      "action": "proposal_apply",
      "proposal_id": "提案ID",
      "option_id": "方案ID",
      "fingerprint": "提案返回的指纹",
      "remove_device_ids": []
    }]
  }
}
```

重复调用必须保持原 operation_id 和请求内容。过期提案返回 `PROPOSAL_STALE`，旧回执重试可读回原结果；失败事务不提交半份设备。部分生成和冲突方案可以作为明确待核对草稿采用，不代表正式业务确认。

## 网页入口

- 项目顶部“按需求生成方案”：独立／共享分支、方案明细、客户或维护者问题、决策依据、改单差异、下一替代方案及整批采用。
- “读取已保存提案”：恢复当前草稿的持久提案，已过期提案仍可查看，禁止覆盖当前草稿。
- 搭配知识 → 按系统版本维护 → 维护角色定义与发布知识包：数量依据、角色配套满足关系、推荐顺序、条件及原文引用。
- 产品清单、Univer 报价、拓扑、正式保存与模板导出继续使用原流程。网页提交和重试采用共用业务服务及检查点。
