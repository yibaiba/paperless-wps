# WPS 下一步编辑：实施与证据

## 范围

基于固定项目资料和工作簿本地变化，提供产品补全、缺配、复用、数量与换型影响预览。跨行修改须明确确认，支持插件独立撤销。正式项目仍通过同步预览和提交保存。本轮不接入新模型。

2026-10-04 的规则与协议变更、测试记录及原生能力矩阵见 [原生补全与规则交付记录](wps-native-rules.md)。原生输入路径尚未接入；既有 WebDialog 是兼容路径，不代表原生单元格灰字通过。

## 验收证据边界

40 例目录序列测试是同源序列回归，不能证明真实改单准确率。仓库内置一份报价模板；data 下存在历史导出和隔离验证文件，不能自动认定为三类独立真实模板。

真实验收需要至少 30 条独立业务轨迹及确认依据、三类模板、macOS 和售前实际 Windows WPS。合成 HTTP 测试和宿主替身仅证明代码行为，不是上述业务与真机验收。当前不得宣称达到 Cursor 同等体验或完成两周试点。

## 性能变更

接受候选后仅读取当前产品行，不再为取得当前行调用整表扫描；以单测禁止该路径重新引入 readRows。查找下一空产品行复用已缓存的占用行，不逐行调用 WPS。完整 completionRequest 的 1,000 行替身测试覆盖连续 20 次查询：1 次初始整表读取、40 次单行读取。实际宿主延迟仍需真机测量。

下一步预览使用共享检查器的业务依赖闭包：当前系统、共享设备关联的系统、配套分配及规则明确声明的房间/项目范围。显式修改的房间、设备和分配身份也纳入检查；项目级规则存在时仍可能涉及全项目，不以裁剪依赖换取通过。返回的 `evaluation_scope` 明确本次检查范围，`configuration` 保留完整临时配置；局部通过不代表全项目通过，正式同步仍全量检查。隔离 HTTP 测试验证增加 1,000 个无关系统后，每次候选检查仍只接收相关系统；这不是实际 API p95 测量。

检查范围保留编辑前依赖，再与编辑后关系合并；共享设备、配套分配被移除后，原关联房间仍显示缺项。局部预览不重新绘制全项目图，原图保留至正式全量处理。

## 业务同步协议 v2

`GET /api/wps/bindings/{binding_id}/context` 读取固定基线与定义。同步请求增加 `schema_version: 2`、`expected_binding_revision` 与明确的 `business_operations`。产品行必须填写真实 kind；省略供货分配表示保留原状态，新设备供货未知，不能默认采购。角色、系统设置和配套关联通过既有类型验证及项目检查重新计算。v1 请求不能改写已经提交为 v2 的绑定。

隔离 HTTP 测试验证：上下文和预览不新增业务实体或修订；软件类型及已有库存保留；过期绑定返回冲突；协议 v2 不允许知识刷新操作。此证据不代表真实红盾资料已确认。

## 已实现的业务路径

- 任务窗格“业务”页选择实际房间、系统和固定知识包，将工作表产品行范围绑定到稳定 ID。新建或修改人数等参数、功能选择不以产品数量代替。没有固定已发布资料时显示缺失原因，不自行发布草稿。
- 手填旧行先解析并明确选择配置、来源和类型；可以关联已有项目设备。用途、环境及供货设置先预览，保留已有字段。确认只写本地元数据与操作日志。
- `POST /api/wps/completion/preview` 将可见行、移除行及明确业务操作覆盖到固定基线。调用共享规划模块的单步角色、配套、容量、复用和检查能力，不生成持久化方案提案，也不枚举整套方案组合。
- 有输入时先处理当前行明确用途；未绑定用途则用固定适用关系识别唯一角色，不把上一行的软件角色强加给硬件。已确认别名随固定目录快照参与检索。空白查询先处理最近修改的容量或配套问题，再补必要角色；未选的可选配套不连续推荐。知识不足返回问题，不等于满足。系列顺序不构成采购依据；没有内置红盾型号顺序。
- 已确认的已有设备数量不跟随需求人数增减。例如库存三台、需求改为两台或四台时，保留三台设备及供货记录，显示需求与分配的差额，请用户确认用途分配或缺量方案；不把需求量写成库存量。主动换型及明确盘点更新仍可预览，纯采购数量调整不受此影响。隔离 HTTP 回归覆盖这一行为，不是已确认红盾容量规则。
- 可直接接受的单行产品修改保留既有灰字路径。有其他产品不等于当前身份有歧义：明确输入唯一匹配、唯一有效方案或已确认规则指定的选择可返回主建议；同等方案、多配置或多来源仍须选择。屏幕外修改先定位、重新查询再确认。数量、删除和配套关联通过差异预览确认，支持预览聚焦后的 Ctrl/Cmd+Enter。
- 异行建议默认显示工作表、行、字段和实际证据摘要，再用 Tab 定位。包含式匹配但不是输入前缀（例如“务器”匹配“服务器”）先展示完整候选，再展开明确选择；不能在灰字为空时直接写入。空行完整灰字、前缀补全和已完整输入的唯一名称仍保留原有接受行为。
- 使用现有空产品行，不插删物理行。移除仅清理已预览的受管字段；数量、备注、公式、未管理列不随删除清理。
- 换型使旧价格失效时明确清除受管价格；未受管价格有旧值时阻止应用并指出位置，请先清除旧价或调整映射后重新预览。仅采用共享报价规则可确定的价格，缺价提示待确认。行扫描使用 Value2 原值，与写入预检查一致，不用千分位或货币显示文字作为金额。

## 编辑日志、恢复与同步

隐藏元数据 v2 按记录分块存储，不把全部日志放入单个单元格。应用前核对本地修订、目标原值、公式和合并状态；先写 prepared 日志，再写单元格、读回核对、保存身份、标记 applied。

隐藏记录的读取缓存只在根索引写入并核对成功后发布。若提交失败，另一页面可能重用那些尚未提交的存储行；原页面不能按相同行号读回失败事务的缓存。双实例共享存储的故障注入测试覆盖索引记录和根指针写入失败；这不是 WPS 多窗口真机验收。

“撤销本次补全”只恢复这一组的单元格、身份和业务操作，不覆盖无关后续修改。手改冲突显示具体位置。中途失败保留 recovery_required 日志与恢复意图；重开后从“检查并恢复本组修改”继续。恢复回执失败重试不会重复追加逆向业务操作。未完成恢复时不能另起成组修改或同步。

撤销/恢复入口按操作编号重新读取持久日志，不信任按钮闭包里可能过期的 applied 快照。已撤销或已恢复的操作重复触发不再修改单元格、业务修订或逆操作；未完成恢复沿用已保存的恢复意图。日志不存在时明确报错，不返回假成功。纯业务关联组、已同步供货逆操作和撤销后手工改值均有故障注入回归；仍不代表真实 WPS 撤销栈通过。

人工用途、环境和供货修改的前值来自 `/sync/preview` 返回的当前临时配置，包含之前未同步的本地操作，不使用旧服务端基线计算逆操作。日志记录原 binding_id，重新绑定后的旧日志不能撤销到新项目。旧日志缺少绑定身份时明确报错，不推测归属。

插件不注册全局 Ctrl/Cmd+Z；内联输入聚焦时才处理插件撤销。实际 WPS 原生撤销栈受到 COM 写入的影响仍须真机验证，不能宣称已接入原生撤销栈。

同步重新扫描可见行、复验业务关联和版本，显式确认后才保存正式项目。请求在本地保留 pending_sync；网络中断或服务端成功而元数据回写失败时，重试相同 operation_id 恢复回执。同步之后撤销生成新的本地变化，保留已经保存的基线。已移除设备的历史行—设备映射仅允许原对应身份恢复。

真实 PostgreSQL 隔离验证曾复现：两个不同操作在同一草稿基线上竞争时，后获得行锁的请求仍使用 ORM 先前缓存的旧修订，触发重复修订数据库异常。共享 `Entities.get(lock=True)` 现在在获得锁时重新载入数据库值，先执行版本冲突检查，而不是捕获数据库错误伪装成功。

2026-10-03 已通过真实 PostgreSQL + HTTP/Bearer 路径验证：同一操作并发只形成一份项目修订；不同操作竞争只有一个成功，另一个返回 409；重建应用实例后仍能取回原幂等回执；更改请求后复用 operation_id 被拒绝。测试使用两个独立令牌，避免认证记录锁意外串行化测试。随机测试 schema 在结束后清理，不写生产业务表。这是数据库集成证据，不是 WPS 真机同步验收，也不是进程崩溃或网络故障注入证明。

异步操作核对物理工作簿与项目绑定。即使复制文件保留相同 workbook_instance_id/binding_id，切换文件后也不把原请求回执写入副本；原文件保留 pending_sync，返回后重试原操作恢复。未完成回执或日志恢复前不能重新绑定。

v1 候选兼容路径同样执行会话校验。切换物理工作簿时取消请求、清空候选与模板；响应到达和接受前再次校验来源，旧候选不能写入新文件。

业务确认、人工身份设置、设置保存和插件撤销在写入入口校验页面所属文件与绑定，不能仅依赖页面卸载时机。内联输入本身也校验创建浮层时的文件与绑定，即使副本的业务修订和单元格原值完全相同，旧浮层输入仍不能写入副本。

旧 WebDialog 兼容路径在无候选、加载或错误时关闭窗口、恢复 OnKey、激活工作簿并用 WPS SendKeys 交还按键；它不是本轮要求的原生路径，也不计入原生验收。原生能力验证包不调用 SendKeys、不创建浮层、不写候选再撤回。不能将旧路径启动检测成功解释为原生编辑支持。

## 增量读取与失效

普通 SheetChange 保留工作表与范围，只刷新受影响行；初次读取和结构变化才重建行索引。1,000 行宿主替身测试证明连续 20 次普通修改不重复整表读取，但它不是 WPS 性能基准。

下一步业务预取键包含物理工作簿标识、位置、本地业务修订、模板修订、绑定/草稿/项目修订及固定目录、知识、定义、决策版本。接受后在当前位置预取下一步决策，不再无条件跳到下一行；服务端按实际差异返回目标位置。定位先验证修订、身份和原值，移动后重新查询，不复用旧差异。错误继续显示，旧响应丢弃。结构变化后的重复产品身份要求重新确认，不猜测行对应关系。

## 独立业务回放

入口 `scripts/wps_business_replay.py` 只请求有鉴权的 completion/preview，不提交项目。私有清单放在本地证据目录，不把客户工作簿或令牌提交仓库。

清单为 `schema_version: 1`，`cases` 每项包含：`id`、`project_id`、`template_id`、`split`（development/acceptance）、`reviewed_by`、`evidence_confirmed`、`evidence`（相对文件 path 与 sha256）、完整 `request`、`expected_edits`、`expected_questions`（问题 code）和/或 `expected_decision`。停止或无匹配案例可以只指定决策状态，但仍须人工核对和证据指纹。期望编辑按 `variant_ids`、`source_ids`、按位置排序的完整 `patches` 和 `business_operations` 比对。同项目不能跨开发/验收集合。未确认资料不能预设采购答案。

```sh
# 令牌由当前环境安全提供为 PRESALES_WPS_REPLAY_TOKEN，不写入清单
env LC_ALL=C perl -e 'alarm 60; exec @ARGV' .venv/bin/python scripts/wps_business_replay.py /absolute/private/evidence/manifest.json --base-url https://intranet.example --acceptance
```

验收模式检查至少 30 条轨迹、三类模板、证据指纹及人工核对字段；不能用目录序列或合成 fixture 补数。脚本单测仅验证评分器本身，不是业务得分。没有真实清单时不输出虚构准确率。

回放分别统计排名正确与初始 Tab 动作。空白行灰字覆盖率只计“首选正确、具有可直接接受的主建议、当前位置且允许 inline 应用”的建议；需展开选择、先定位其他行或进入数量/关联预览的建议仍可计入 Top-1/Top-3，但不能冒充一次 Tab 的灰字覆盖。旧响应没有主建议时仍按单候选判断。活动工作表及行列缺失时明确报错。`initial_tab_action` 对齐插件状态机的初始非 IME 状态，不验证真实按键与焦点。

报告的 `incorrect_direct_edits` 是只读 API 回放发现的错误直接接受建议数，不是已执行的工作簿误写数。`evidence_scope: read_only_api_replay` 和 `host_writes_verified: false` 明确这一边界；零错误实际写入仍须真机矩阵确认。
