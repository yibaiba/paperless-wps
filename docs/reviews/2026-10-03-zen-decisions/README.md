# 知识与 ZEN 决策接入验收

本轮在既有模块化单体中增加 `zen-v1` 决策运行时。旧项目继续用 `python-v3`，新项目使用 ZEN；旧项目通过改单预览明确升级。运行时升级与资料、价格刷新独立，不替用户确认真实搭配。

## 使用方式

- 搭配知识 → 按产品维护 → 选择配置 → 添加互斥 / 必选组合。
- 选择系统、房间或项目范围，添加已有角色或配套需求。全部需求必选、至少一项、互斥分别维护。单个需求内的多个配置是替代候选，数量继续采用原角色或配套依据。
- 候选和项目检查使用相同决策服务；MCP 方案生成会展开已确认必选需求并沿原候选搜索继续检查。缺数量、缺关系、未确认资料仍显示未知；不默认采购一件。
- 旧项目 → 更多操作 → 预览本次改单 → 预览采用 ZEN → 应用到草稿。可撤销、重做，保存后生成新版本。原版本不改写。
- 已确认的组合冲突提供选型或配套处理入口；缺少依据仍指向知识维护。

## 架构和边界

Python 负责业务身份、范围、分配、方案分支、存储和报价；ZEN 执行受控条件、允许/禁止、替代组、组合、共享条件和容量比较，继续负责数量公式。没有新增模型调用、求解器、依赖或服务。

编译记录固定引擎版本、编译版本、哈希、关系修订及节点来源映射。编译/执行错误明确失败，不降级为 Python。候选查询、项目检查及 MCP 固定版本保护共用这套实现。

知识包单产品试查仍明确只检查该角色适用条件。需要整套配套、共享或组合上下文时使用项目候选及项目检查；不能把单产品通过当成整套通过。图编辑器未加入。

## 已完成验证

- 37 项真实 ZEN 条件语义测试：等值、集合、范围、单位、缺值、启用条件、替代组、拒绝优先、容量及引擎错误。
- 运行时升级、固定快照、知识包只读元数据回传、候选/项目一致性。
- 互斥、全部必选、至少一项、跨房间边界、缺数量、实际用途关联、候选冲突、必选角色生成和配套满足角色的去重。
- 真实 stdio MCP 通信及提案协议测试通过；HTTP 与 MCP 使用相同服务。
- 相关回归批次分别为 31、27、35 项通过；SQLite 下 3 个 PostgreSQL 专用项跳过后，另用 PostgreSQL 独立 schema 执行并发相关 7 项，全部通过。
- 前端 TypeScript 检查、生产构建、17 项编辑操作及增量表格投影测试通过。构建仍有既有 Univer 大包警告，本轮未减包。
- 实际浏览器使用隔离数据库：新增组合草稿、重新编辑回填；旧项目升级预览、应用、撤销、重做、保存 v2、刷新恢复；互斥项目显示冲突和知识依据入口。截图见本目录。

后端每项通过 pytest-timeout 限制 60 秒，每批通过 subprocess.timeout=60 限制。测试资料未写入业务库。

## 性能实测

同一机器、SQLite 隔离资料、同一条已确认适用条件及相同设备/角色，7 次全量项目检查的中位数（包含准备、存储访问、计算及投影，不包含 HTTP/浏览器）：

| 设备行数 | 原 Python | ZEN | SQL 次数（原 / 新） |
|---|---:|---:|---:|
| 100 | 50.06 ms | 62.01 ms | 15 / 19 |
| 500 | 266.51 ms | 325.39 ms | 15 / 19 |

ZEN 增加受控执行、哈希及编译版本校验，有额外成本，本轮不宣称提速。500 行增加约 59 ms。定位后已将相同容量比较、空条件和相同规则输入结果限制在一次请求内复用；没有跨草稿复用检查结论。源码和逐次结果分别在 `benchmark.py`、`project-benchmark.json`。早期未优化容量重复执行时接近 1 秒的样本不作为最终基线。
