# 来源约束与多角色配套绑定 review

基线：`ec7bb8d`。本轮检查需求来源、候选生成、角色配套绑定、人工分配保护和报价后的检查结果。真实业务数据未修改；其他 WPS 改动及原有 review 目录未纳入提交。

## 已复现并修复

### 1. 明确指定的产品来源未参与日常检查

生成偏好支持 `source_id`，但产品约束检查只比较配置 ID。两个来源属于同一配置时，改为指定另一来源，当前设备仍保留旧来源，检查却没有显示来源冲突。

现在按角色关联的全部设备核对指定来源，直接关联和按数量分配共用此检查。冲突返回原有 `product_constraint_conflict` 代码及需求依据；报价增量修改不能消除它，保存仍允许保留问题，但正式确认不可通过。人工分配不会为满足偏好而被静默改写，明确调整来源要求后冲突解除。

### 2. 指定第二候选的来源导致整个生成请求失败

来源属于第二个候选时，生成器仍先尝试第一候选，在构造设备时抛出“指定资料来源不属于候选配置”，未继续寻找实际上可用的候选。

现在先在候选排序阶段应用来源约束，再生成设备；仍保留设备构造阶段的来源归属校验，不吞掉错误。验证先生成提案不会修改实际设备，明确采用后使用指定来源对应的配置。

### 3. 多个同类角色的配套服务器被按顺序关联

角色定义通过其他角色的某个配套需求满足时，原生成逻辑只查找同系统的第一条父角色需求。两条终端需求分别需要两台服务器时，服务器角色会静默关联第一台。

现在汇总同系统全部匹配父角色的配套设备：唯一设备才能自动建立角色关联；多个不同设备返回 `role_fulfillment_missing`。改单后原自动关联已经不再唯一时，解除自动角色引用并保留设备及采购清单；人工关联保持原样，并在提案中保留待核对问题。同一系统级需求明确指向同一台服务器时仍可唯一关联，不因多个父角色误判。
