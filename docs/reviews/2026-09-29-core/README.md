## 1. P1：保存结果读取失败后，新编辑会复用旧保存回执

位置：`frontend/src/features/configuration/projects/drafts/usePersistentDraft.ts:110–122`；后续覆盖发生在 `projects/useProjectRequests.ts:62–68`。

触发：先保存配置 A。后端检查和正式保存均成功，获取工作草稿也成功，但最后读取正式项目失败。此时 `savePending.current` 留下捕获 A 的闭包。用户继续编辑为 B，草稿已同步，再次点击保存仍使用 A 的 check/save 幂等键。

结果：服务端正确返回 A 的旧幂等回执；前端读取返回 A，并当作这次保存 B 的结果。`currentMatches(before)` 比较的是第二次点击时的 B，无法识别返回的却是 A，因此可用 A 覆盖页面并显示保存成功。后续自动同步还可能将页面回退同步回工作草稿。

复现：执行实际 TypeScript hook，注入遵循现有修订及幂等语义的请求适配器，仅令最后一次读取失败。输出 `currentDraft={note:B}`、`saveReturned={note:A}`，两次保存使用相同 operation ID，断言失败。见 `save-retry-probe.cjs` 与同名日志。本项是状态单元故障注入，不是本轮真实浏览器网络故障验收。

修复方向：未完成的保存要绑定发起配置及修订，分别记录“已提交”和“待读取”；重试只恢复原操作结果。其后出现新编辑，必须建立新保存操作，并按返回配置/修订核对，不把旧回执视为新修改成功。

## 2. P1：旧配置编辑入口绕过参数变化后的搭配复核

位置：`backend/src/presales/configuration/catalog/service.py:71–96`。

产品整理页及按产品维护台仍通过 `VariantEditor` 调用 `PUT /api/configuration/variants/{id}`。此入口直接保存参数，既不比较技术参数变化，也不建立待复核影响。新的更新批次 `correct` 路径才执行 `affected` 并写入 `review_requirements`。

复现：已有 x86 配置及已确认适用关系，经旧编辑入口将 CPU 架构改为 arm64，查询候选仍返回 `pass`，没有待复核事项。确认配置参数不等于重新确认所有旧搭配关系。

修复方向：所有技术参数写入共用影响计算和修订逻辑；保留显示文字修改的轻量路径及旧项目固定快照。不能只修新增更新工作区。

## 3. P1：包外关系未经资料包发布就影响选型

位置：`backend/src/presales/configuration/projects/services/definition_snapshot.py:33–47`。

`project_knowledge` 将全量知识快照与包内固定关系做并集。包只固定已有成员的修订，无法限制新增包外关系参与适配和计算。

复现：先发布一个明确推荐配置 A 的包；随后新增一条针对该系统的已确认禁用关系，但不加入或重新发布这个包。新项目仍选择原包，却自动改选配置 B。变化来自包外关系，不来自包修订或产品变化。

修复方向：采用资料包时，按固定成员及显式公共依赖构造有效知识；无包历史项目保持既有语义。若需要紧急全局禁用，应单独明确表达并展示来源，不能和“采用固定包版本”混在一起。此发现不表示已经保存的旧快照被直接改写。

## 4. P1：共享模式会复用未获允许的客户已有设备

位置：`backend/src/presales/configuration/projects/planning/accessory_choices.py:101–107`。

只要选择共享部署、配套声明可共享、设备数量为一，`shared` 分支就绕过 `reusable_device_ids`，且没有区分新生成设备与仅登记在项目中的客户资产。

复现：两台客户已有服务器，未对任何一台声明允许复用；以共享模式生成，服务端配套自动关联 `stock-a`。供货已有状态被保留，本次不会生成对应新购服务器。

修复方向：跨系统共享新生成设备，与允许改用客户已有资产分开判定。已有设备必须有明确复用选择；共享可行性和容量检查不能替代这个选择。

## 5. P2：配套服务器替代方案漏掉其他可复用实例

位置：`backend/src/presales/configuration/projects/planning/accessory_choices.py:98–115`；调用方 `planning/accessories.py` 对每个配置只接收一条复用分支，再生成新购分支。

复现：需求一台服务器，显式允许复用同配置的 `stock-a`、`stock-b`。第一方案使用 A；下一方案直接新购；继续取方案已 exhausted，B 从未进入候选组合。直接角色选择上一轮已修复类似枚举，配套路径仍遗漏。

影响：Agent 无法提出使用 B 的替代方案；A 与其他系统发生后续冲突时，也无法回溯尝试 B，可能不必要地增加采购。

修复方向：按实际设备 ID 枚举复用分支并去重，保持后续共享、容量和预算检查及按需返回；不要把一款配置的第一台实物等同于全部候选。

## 复现材料
