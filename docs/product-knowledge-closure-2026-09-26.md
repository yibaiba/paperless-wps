## 已实现的业务闭环

来源核对增加三种互斥结果：关联配置、明确阻塞、未处理。阻塞和重新关联使用同一来源修订号，竞争写入返回明确冲突；原 `/source-links` 和 `/independent-sources` 保持兼容，新增 `/source-blocks`。

产品属性由统一定义接口提供名称、类型、单位和别名。首批覆盖 CPU 架构、CPU 数量、单 CPU 核数、操作系统及版本、软件版本、内存、终端／用户容量、宽高深、屏幕尺寸、服务器类型和部署形态。历史自定义字段继续保存，界面标记为未注册字段，不改写旧配置或项目快照。

项目检查新增统一“设备使用情况”投影。直接角色选择、软件配套服务器、多个需求关联同一设备以及配件／授权数量分配，都转换为同一份设备—角色关系。清单投影和项目页面复用该结果，因此通过配套关联的服务器会显示它实际服务的系统，不再显示为未分配。

角色资源增加 `applies_to` 和 `target_need_key`。软件的内存、CPU 等要求可以明确交给 `server` 配套需求承担；检查不会再拿软件配置的属性当作服务器容量。共享服务器会合计所有消费者的同单位资源，与实际服务器配置比较。

共享检查的结果语义如下：

- 已确认共享依据覆盖全部系统角色，条件通过且容量足够：通过。
- 已确认规则禁止共享或容量不足：冲突。
- 缺少共享依据、角色资源或服务器容量：资料不足，允许保存但不表述为已验证。

## 红盾 Windows 与会议预约隔离试点

隔离项目包含一个会议室、红盾 Windows 无纸化、会议预约、两套服务端软件和一台 X86 服务器。两套软件分别产生 `server` 配套需求，第二套需求通过“关联已有设备”显式使用第一台服务器。

最终项目清单为两套软件和一台服务器。服务器设备使用明细同时列出：

- 红盾 Windows 无纸化 / 服务端软件（配套）
- 会议预约 / 服务端软件（配套）

隔离容量为 128GB、32 核，两个系统合计要求 64GB、12 核，容量检查通过。共享知识只有草稿，所以共用部署仍显示“资料不足”，待确认事项明确指出缺少覆盖这两个系统角色的已确认共用依据。

单元测试另覆盖两台独立服务器分别计数、加入隔离确认共享规则后的通过结果、160GB 对 128GB 的容量冲突、重复分配、删除设备后需求恢复。测试规则只存在于测试数据库。

## 仍需业务确认

系统已经能完整表达和检查独立部署、显式共用、资源汇总和资料缺口，但不能据现有名称判断红盾与会议预约允许共用服务器。需要维护者提供软件兼容、部署方式、容量口径和共享条件后，才能把共享草稿改为已确认。首个真实客户项目仍需房间、系统版本、终端数量、部署环境、已有设备和共享要求。
