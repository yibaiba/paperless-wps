# 无纸化配置规则说明与验证

日期：2026-09-24。

本轮补充多型号合计容量、必须配套、候选配套检查、按系统最低数量和备注差异检查。沿用 FastAPI、PostgreSQL、真实 GoRules ZEN 和 Ant Design，没有增加依赖，没有接入 LLM。

## 操作与计算语义

1. 在“配套规则”选择具体来源版本和触发产品；允许共同计量的型号放入同一条规则的“共同合计的其他型号”。
2. 选择关系：数量配套、必须配套，或必须配套且人工选择候选。后者配置首个配套及其他候选。
3. 选择计算方式：按用量相乘、按容量合计后向上取整、或每个系统最低数量。填写来源、适用条件、维护人。
4. 先保存草稿并试算，适用条件确认后再启用。试算输入是这条规则所有触发产品的合计数量，只验证数量算式。
5. 项目清单的“区域 / 系统”字符串是当前计算边界。允许共用的设备使用同一系统标识；跨房间共享时可在行备注记录房间。尚无独立房间、子系统和资源池层级。
6. 打开“配套计算”，查看必配缺量、候选待选择、草稿未确认、资料待核对等提示。明确目标的缺量可以勾选补入；候选由人回到项目清单选择添加，再重算。

### 共享容量

同一条规则选择 A、B 型号，容量 50：同系统 A=20、B=20，合计 40 后计算得到 1。另一系统 A=30、B=30，则该系统单独得到 2。保留各来源数量、合计输入、ZEN 执行轨迹和规则版本。

不同容量规则仍代表独立需求，计算后相加。维护者必须将同一共享需求写为一条多来源规则。系统不会凭型号或备注推断能否共用、能否分片，超过容量后的结果不等于已经验证部署可行。

### 必配与候选

- 明确目标的必配：依数量规则计算需求，不足时标出“缺少必配”，可选择补足。
- 系统最低数量：只要规则被触发，该系统至少需指定数量。例如至少一台主机，不会按每个升降器型号重复加一台。同目标的最低数量取最大值，与其他数量规则的合计需求再取较大值。
- 候选关系：主目标与其他候选合计现有数量，缺量显示“需要选择配套”，不会自动把候选全部加入。足量只显示“候选合计数量已满足”，不表示角色、协议或兼容性已经验证。
- 计量必须使用一致单位；重复来源、重复候选、来源与目标重叠、不存在的产品会明确报错。
- 多条候选关系目前分别检查，不进行全局库存预留或独占资源分配；不能用它替代跨规则的资源求解。

旧规则没有新增字段时保持原单来源、数量配套的行为，旧应用记录仍可查看。规则字段存于既有 JSON 中，无须改表或重建数据库。

## 验证结果

- 完整后端 **56 项通过**，无跳过、无 xfail，34.80 秒。真实资料专项18项、原回归29项、新规则边界9项。
- 配置了真实 PostgreSQL 测试连接和原始 Excel 路径，随机独立 schema 测试后清理；整组及每项测试均设置60秒硬超时。
- 覆盖多型号40/50只需1台、不同系统独立计算、重复系统必配主机不重复加、候选20缺20/已有19缺1/已有20足量、其他系统不抵扣、源集合变化后旧预览失效及版本历史保留。
- 覆盖草稿可见但不计算、备注差异单元格证据、核对状态同步、重查不重复且保留历史，以及原有两项PostgreSQL并发回归。
- 原“从原文自动识别主机”的测试改为显式维护必配关系后验证漏配；无规则时仍只显示未覆盖，没有伪造自动理解功能。
- Ruff格式和静态检查通过；前端TypeScript检查和生产构建通过。原有共享包大于500kB、Starlette测试接口弃用提示仍存在。
