# 艾索售前工作台


[方案拓扑](docs/drawio.md)：本地 draw.io 完整编辑器、设备/机柜图形库、产品绑定、系统分组、关系维护、版本保存、设备汇总和必配关系生成草稿规则。

独立的售前平台开发项目。前端使用 **TypeScript + React + Ant Design**；表格、表单、导航、抽屉、弹窗和反馈都使用组件库。后端使用 **Python + FastAPI + SQLAlchemy + PostgreSQL**。

## 已实现

- 产品属性单条/批量维护及版本历史；按系列、功能、接口/协议、适用系统匹配规则，支持例外排除与匹配预览。详见 [产品属性与规则复用](docs/attribute-rules.md)。

- 导入当前艾索产品 Excel 格式，按文件内容识别重复导入。
- 按版本查看、搜索和筛选产品来源记录，查看参数、备注、招标参数、原始价格和工作表位置。
- 保留同型号的不同配置、总表和分表记录、隐藏工作表标记、合并单元格的说明及位置。
- 列出同型号名称差异、完整参数差异、配套备注差异和名称字段可能错位的记录，展开查看来源证据。
- 对差异记录处理结论、人员和依据；保留每次处理历史，可重新设为待确认，按型号、类型和处理状态筛选。
- 在产品详情、选品表单和项目清单展示关联差异的当前状态，直接跳转到该来源版本的核对依据。
- 创建项目；选择具体来源产品；按区域/系统填写数量和备注；编辑或移除清单行。
- 加入清单时保存来源配置快照，后来导入新版资料不会直接覆盖旧清单。
- 接入 GoRules ZEN 0.53.0：维护配套规则、独立试算、规则版本历史、项目缺量预览和选择补入，保留实际引擎执行轨迹。

本版是本机运行的开发版本。资料核对支持处理结论和历史，尚未实现原始参数修订和正式产品主数据发布。项目主设备由人选择，可用已配置规则计算配套缺量；尚未实现自动主设备选型、价格计算、审批和完整清单版本历史，也未连接 LLM、MCP、OA 或微盘。当前无登录和权限管理，处理人由手工填写，不是已认证身份；服务仅绑定本机地址。

## 配套规则与计算

规则引擎直接嵌入 Python 后端，使用 `zen-engine==0.53.0`，没有额外的规则服务器、云服务或模型请求。前端仍使用 Ant Design 维护业务字段。相关 API 由 GoRules ZEN 决策图中的表达式节点实际执行数量计算；不是界面模拟，也没有引擎失败时换成硬编码结果的路径。

1. 打开“配套规则”，选择具体触发产品、配套产品、计算方式和比例，记录依据及维护人。
2. 保存草稿后，在“数量试算”输入数量核对结果；确认适用范围后在规则配置中改为“启用”并保存。修改规则会保存新版本，旧版本仍可查看。
3. 打开项目清单，按区域/系统添加主设备和已有配套，再点击“配套计算”。
4. 查看需求、已有、应补、超出数量以及所命中的规则依据。选择需要的建议后点击“将所选缺量补入清单”。
5. 在“应用记录”查看当时的规则版本、原始输入、需求和补入数量。后续改规则不会重写既有清单或历史。

支持三种计算：

- 按承载量：`ceil(该组触发数量 / 每件配套承载量)`，如 21 件、每件配套承载 2 件，需求 11 件。
- 按单件用量：`该组触发数量 × 单件配套用量`，保留计算结果，不自动取整；可用于明确按件固定用量的线材等。

计算按区域/系统的精确分组名称执行。同一来源产品的多条清单行先合计再算，多条规则指向同一配套时各自需求相加；该组已有配套总量只抵扣一次。例如需求 11、已有 3，应补 8。只新增缺量行，原有人工行不覆盖，超出量不自动删除。

按系统最低数量：出现触发设备时至少配置规则指定的数量；例如多型号升降器共用一套系统，检查至少有 1 台会议主机。这不是容量充分性判断。

配套关系分为数量配套、必须配套和人工选择候选。候选关系合计已选候选的数量，不自动全部补入，也不验证主席/代表角色分配。未启用的相关草稿及资料待核对项会在计算面板单独显示。

规则绑定来源记录 ID，不能仅凭型号相同跨表、跨配置或跨版本自动套用；规则指向的新旧产品需要维护人明确选择。草稿和停用规则不参与项目计算，但仍可独立试算。

当前为单层计算：新增配套不在同次计算中继续递归触发下一层规则。支持已明确共享的多型号合计，但没有全局容量分配、兼容性或互斥求解、路径测量、损耗或定制尺寸计算。未触发规则的清单行单独列出，不被视为已完成配套检查。独立数量规则仍会相加；共享容量必须维护在同一条规则中，不能给每个型号各建一条容量规则。

预览包含清单及规则的摘要；应用时后端重新计算并验证摘要，不接受前端提交的数量。清单或规则变化时明确提示重新计算。项目编辑和规则应用使用同一项目事务锁，避免重复请求多加配套。

已按本次 Excel 整理 `EG-620D → BE6/T` 的草稿。`AI智能纪要!F26` 明确“一盒带两只话筒”；具体会议单元的连接方式、回路及适用范围尚需核实，所以草稿没有启用。试算结果证明数量执行正确，不代替工程适配确认。

参考：[ZEN 项目](https://github.com/gorules/zen)、[官方 Python 接入说明](https://docs.gorules.io/developers/sdks/python)。

## 资料核对流程

1. 在“资料核对”选择来源版本，可搜索型号、筛选差异类型和处理状态。旧版本可点击“重新检查资料差异”补入新检查发现的问题，已有处理历史保留。
2. 点击“查看与处理”，对照工作表及单元格原文。
3. 记录结论：待确认、确认为不同配置、仅表述不同、原资料有误待修订；填写处理人和本次依据后保存。
4. “处理历史”保留历次结论；需要复核时可重新设为待确认，并说明原因。

结论只作用于当前导入版本。新版资料重新导入后，不自动继承旧版结论。同型号的名称/参数/备注差异关联该版本的同型号记录；字段错位问题仅关联具体来源行。原资料有误仍作为待跟进项，不会被计入已确认配置或表述差异。

保存处理结果不会改写产品参数、合并型号或调整清单数量。清单仍保留加入时的参数快照，另列显示来源版本当前的核对状态。暂无差异或已有结论不代表完成产品兼容性检查。

若两个人同时处理同一差异，后提交的旧版本请求返回明确冲突；关闭处理窗口、重新打开查看最新历史后再提交，避免覆盖已有依据。

## 运行

需要 Python 3.12+、Node.js 24 和已运行的 Docker。

在项目根目录执行初始化：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e './backend[dev]'
python3 scripts/setup.py
docker compose up -d --wait --wait-timeout 90
npm --prefix frontend ci
```

启动后端，保持终端运行：

```sh
.venv/bin/uvicorn presales.main:app --host 127.0.0.1 --port 8016
```

另开终端，在项目根目录启动前端：

```sh
npm --prefix frontend run dev
```

访问 <http://127.0.0.1:5176>，点击“导入产品 Excel”。后端 API 文档位于 <http://127.0.0.1:8016/docs>。前端开发服务把 `/api` 转发到后端，把 `/diagram-editor/` 转发到本地绘图服务；部署说明见 [图纸工作台](docs/drawio.md)。

关闭前后端终端进程即可停止应用。`docker compose stop` 停止数据库并保留数据卷。

## 数据与导入边界

`.env` 由初始化脚本随机生成数据库密码，只创建一次，不覆盖已有配置，已加入 Git 忽略。PostgreSQL 的本机端口为 25432，数据保存在 Docker 数据卷中。前端页面刷新和服务重启不会丢失导入结果。

目前导入器适配这份报价清单的列名：必须在同一行找到“产品型号”“产品名称”“性能描述(完整参数）”。其他格式会明确报错，需要增加对应的格式适配；尚未实现可视化字段映射。只读取实际存在的单元格，不遍历因格式产生的上万空列。

导入保存结构化文本、来源位置和文件摘要，不保存原始工作簿、图片或批注。请继续保留原始 Excel。公式单元格不读取缓存结果、不重新计算；导入不等于复刻 Excel 报价工具。当前价格列按原文保存，不自动解释“按项目申请”等说明。

“来源记录数”包含总表/分表重复和配置变体，不能作为唯一产品数。“待核对差异”是内容差异提示，不意味着所有差异都是错误；没有自动判断停产状态、PoE 支持、跨产品兼容性或服务器能否共用。

## 开发结构

```text
backend/src/presales/
  catalog/    Excel 读取、来源解析、差异检查、核对历史和数据存取
  projects/   项目清单、输入验证和配置快照
  rules/      ZEN 决策图、配套规则版本、项目计算与应用记录
  configuration/search/  产品搜索文档、pgvector、模型适配和索引任务
  storage.py  数据库映射及连接工厂
  api.py      HTTP 接口与依赖注入
  main.py     应用装配
frontend/src/
  features/catalog/   产品资料与差异查看
  features/projects/  项目清单与编辑表单
  features/rules/     规则维护、试算、缺量预览和应用记录
  shared/             请求、类型及页面公共组件
```

旧模块启动时创建缺失数据表。新配置模块提供显式增量迁移 `scripts/migrate_configuration.py`，不重建数据库；以后修改既有表结构仍须增加迁移。

本轮核对流程新增 `review_events` 表，通过现有启动流程创建；没有修改已有表结构或清理既有产品数据。

规则引擎接入另新增 `accessory_rules`、`rule_revisions`、`rule_applications` 三张表，同样不改变已有表结构。更新依赖并重启后端即可创建。

## 产品搭配知识与统一项目配置

产品整理、搭配知识和项目“需求选配与拓扑”组成业务主流程。候选筛选、环境检查、配套数量和已有设备抵扣都由结构化知识、Python 业务代码与内嵌 ZEN 计算完成，不依赖模型实时响应。AI 资料整理只是可选的录入助手；未配置模型时，人工仍可完整维护知识和使用项目配置。

旧配套规则可从“搭配知识”统一迁移：原规则和历史继续保留，迁入内容保持草稿，重复迁移不会产生副本。“每组”等口径不明确的规则必须先补充系统、房间或项目范围，不能直接用于补料。统一项目计算支持设备、系统、房间和项目四种范围，并以明确的分配记录核对已有配套；软件、授权、硬件和配件分别计量。

当前业务库的五套无纸化工作表共有 144 条来源，已全部建立独立配置归属；全工作簿 459 条来源中已整理 163 条。5 条旧规则已迁入统一知识库且全部保持草稿。红盾 Windows 试点已确认 RS-MSC100 服务端软件和 PCS-6580T 桌面终端的已知操作系统条件；容量、共享部署、授权以及升降器完整配套仍显示资料不足，未作为整套方案验收。

功能、数据状态、后台工作进程启动方式及验收范围见 [配置平台实施记录](docs/configuration-implementation.md) 和 [验证记录](docs/configuration-verification.md)。

新增依赖通过 `.venv/bin/pip install -e './backend[dev]'` 安装；升级后先运行 `.venv/bin/python scripts/migrate_configuration.py`，再重启后端。AI 资料整理与产品智能索引分别使用以下后台工作进程：

```sh
.venv/bin/python -m presales.configuration.extraction.worker
.venv/bin/python -m presales.configuration.search.worker
```

产品整理页新增“智能索引”，项目候选新增“已知候选、智能查找、全部产品”。智能查找使用 PostgreSQL pgvector、Embedding 和 Reranker，只负责召回与排序；兼容性、配套和数量仍由结构化知识、Python 与 ZEN 决定。未配置检索模型时，现有产品、知识和项目流程不受影响。详细说明见 [产品智能召回与候选排序](docs/semantic-product-search.md)。
